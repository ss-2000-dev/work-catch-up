# GA4の基礎知識

対象読者: GA(Googleアナリティクス)に触れたことがない、あるいはUA時代の知識で止まっている人向け。「GA4とは何か」「何が測れて何が測れないか」「POと会話するための用語」を整理します。

実装(実際に書くコード)は [GA4の実装ガイド.md](GA4の実装ガイド.md) を参照してください。

---

## 1. GAとGA4の関係

**GA(Googleアナリティクス)** は、Googleが提供するWebサイト/アプリのアクセス解析ツールの総称です。無料で使える範囲が広く、事実上の業界標準になっています。

バージョンの変遷を押さえておくと、ネット上の古い記事に惑わされずに済みます。

| 世代 | 通称 | 状況 |
|---|---|---|
| 〜第3世代 | **UA(ユニバーサルアナリティクス)** | 2023年7月1日にデータ収集停止、2024年7月1日に完全終了(過去データも参照不可に) |
| 第4世代 | **GA4** | 現行。2020年登場、現在新規に作れるのはこれのみ |

**重要**: 「GA」と言われたら、今の現場ではほぼ確実に**GA4**を指します。ただしWeb上の解説記事は今もUA前提のものが大量に残っており、用語も設計思想も違うため、**UA向けの情報をそのまま適用すると噛み合いません**。調べ物をするときは「GA4」で検索する癖をつけてください。

## 2. GA4の最重要コンセプト: すべては「イベント」

UAとGA4の最大の違いはデータモデルです。ここだけは押さえてください。

### UAの考え方(過去のもの)

「ページビュー」「イベント」「トランザクション」など、**種類の違うヒットが別物として存在**していました。イベントには`カテゴリ / アクション / ラベル`という決まった3つの枠がありました。

### GA4の考え方(現行)

**すべてが「イベント」に統一されました。** ページの表示も、ボタンのクリックも、購入も、すべて「イベント」という同じ形をしています。

```
イベント = イベント名 + パラメータ(付随情報、任意の数)

例:
  page_view          { page_location: "https://example.com/tickets/1", page_title: "チケット詳細" }
  ticket_status_change { from_status: "todo", to_status: "in_progress" }
  purchase           { value: 5000, currency: "JPY", transaction_id: "T-001" }
```

カテゴリ/アクション/ラベルという固定の枠は無くなり、**イベントごとに好きな名前のパラメータを付けられる**ようになりました。この柔軟さがGA4の強みであり、同時に「設計しないと後で分析できないデータが溜まる」という難しさでもあります。

### イベントの4分類

開発者・POとして知っておくべき分類です。**どれを使うかで、実装が必要かどうかが変わります。**

| 分類 | 実装の要否 | 説明 | 例 |
|---|---|---|---|
| **自動収集イベント** | 不要 | 計測タグを入れるだけで自動的に飛ぶ | `first_visit`, `session_start`, `user_engagement` |
| **拡張計測機能イベント** | 不要(管理画面のON/OFFのみ) | GA4の管理画面でONにするだけで自動計測される | `page_view`, `scroll`, `click`(外部リンク), `file_download`, `form_start`, `form_submit`, `video_start` |
| **推奨イベント** | **必要** | Googleが名前とパラメータを定義済み。この名前で送ると標準レポートで綺麗に見られる | `login`, `sign_up`, `search`, `purchase`, `add_to_cart` |
| **カスタムイベント** | **必要** | 自分で名前を決めて送る。業務固有の操作はこれ | `ticket_status_change`, `csv_aggregate_complete` |

**開発時の判断基準**: まず「拡張計測機能で自動的に取れないか」を確認し、取れないものだけコードを書く。次に「推奨イベントに該当する名前がないか」を確認し、あればその名前を使う。どちらでもないものだけカスタムイベントにする、という順で考えます。自前で作りすぎると、標準レポートで何も見えないGA4が出来上がります。

## 3. GA4で計測できること

### 標準で(ほぼコードを書かずに)取れるもの

- **ページビュー**: どのURLが何回見られたか、どの順で見られたか
- **ユーザー数・セッション数**: 訪問した人数、訪問回数
- **流入元(参照元/メディア)**: 検索エンジン経由か、広告経由か、直接アクセスか
- **デバイス・ブラウザ・OS・画面解像度**
- **地域(国・都道府県レベル)**: IPアドレスから推定。番地レベルではない
- **エンゲージメント**: 滞在時間、スクロール到達、外部リンククリック、ファイルダウンロード
- **離脱/直帰の傾向**: どのページで見るのをやめたか

### コードを書けば取れるもの

- **業務固有の操作**: 「チケットのステータスを変更した」「CSVをアップロードした」など、画面上の任意の操作
- **フォームの途中離脱**: どの入力項目まで進んで諦めたか
- **エラーの発生**: どの画面でどんなエラーが出たか(エラー監視ツールの代わりにはならないが、傾向は掴める)
- **ログインユーザーの横断分析**: `user_id`を送ることで、同じ人がPCとスマホで使った行動を1人として繋げられる
- **eコマース**: 商品閲覧→カート追加→購入の一連の流れと売上金額

## 4. GA4で計測できないこと・苦手なこと

**ここがPOとの認識ズレが起きやすい最重要ポイントです。** 「GAで見れるでしょ?」と言われたときに、できないことを説明できる状態を目指してください。

### 規約上「やってはいけない」こと

- **個人情報(PII)の送信は禁止**。メールアドレス、氏名、電話番号、住所などをGA4に送ることはGoogleの利用規約違反です。アカウント停止・データ削除のリスクがあります
  - 「誰が使ったか知りたい」と言われても、**メールアドレスをそのまま送ってはいけません**。代わりに、個人を特定できない内部IDを`user_id`として送ります
  - **URLにメールアドレスや氏名が含まれている場合、`page_location`として自動送信されてしまう**ので要注意です(設計段階で気づくべき点)

### 技術的に取れない・精度が落ちるもの

| できないこと | 理由 |
|---|---|
| **完全に正確な数値** | 広告ブロッカーやトラッキング防止機能で計測タグ自体がブロックされる。一般に**数%〜30%程度**の取りこぼしが起こりうる |
| **個人単位の行動追跡(誰が何をしたか)** | 規約上も設計上も不可。あくまで統計的な傾向を見るツール |
| **サーバー側だけで起きた処理** | ブラウザ上のJavaScriptで動くため、バッチ処理やAPI単体の呼び出しは計測されない(別途Measurement Protocolという仕組みが必要) |
| **長期の個人追跡** | ブラウザのCookie制限(特にSafariのITP)により、再訪問時に「新規ユーザー」として数え直されることがある |
| **リアルタイムの厳密な集計** | 通常、レポートへの反映には数時間〜24時間かかる(リアルタイムレポートは直近30分のみ、項目も限定的) |
| **無制限の過去データ参照** | イベントデータの保持期間は既定2ヶ月、設定を変えても最長14ヶ月(標準版の場合)。それ以前の生データは消える |
| **売上・在庫などの正確な基幹データ** | GA4はあくまで行動ログ。金額の正確性は基幹システム/DBが正であり、GA4の数値は必ずズレます |

### POによく聞かれるが、答えに注意が必要なもの

- **「どのくらいの人が使ってる?」** → ユーザー数は出るが、**ブロックされた分は含まれない**、かつ**同じ人が別ブラウザで来ると別人として数えられる**。「正確な実人数」ではなく「傾向を見る数字」であることを合意しておく
- **「このボタン、押されてる?」** → 実装していなければ**過去に遡って取ることはできません**。GA4は「事前に仕込んだものしか取れない」ツールです。ここが最大の認識ズレポイント
- **「データ、去年のと比べたい」** → 保持期間(既定2ヶ月/最長14ヶ月)を超えていると詳細分析はできない。長期保存したいならBigQueryへのエクスポート設定を**事前に**しておく必要がある

## 5. POと会話するための用語集

会議で飛び交う言葉です。UAとGA4で意味や名前が変わったものが多く、ここを揃えておくと会話が早くなります。

| 用語 | 意味 | 注意点 |
|---|---|---|
| **イベント** | GA4で記録されるすべての行動の単位 | GA4ではページ表示もイベント |
| **パラメータ** | イベントに付随する情報 | 事前に設計しないと、後から「あの情報も取っておけばよかった」となる |
| **ユーザー** | サイトを訪れた人(ブラウザ単位で識別) | 厳密な実人数ではない |
| **セッション** | 一連の訪問のまとまり | 既定では**30分操作がないと切れる**。日をまたぐと別セッション |
| **エンゲージメントのあったセッション** | 10秒超の滞在、2ページ以上の閲覧、またはコンバージョン発生のいずれかを満たすセッション | GA4独自の概念 |
| **エンゲージメント率** | エンゲージメントのあったセッションの割合 | **直帰率はこの裏返し**(1 - エンゲージメント率)。UA時代の直帰率とは定義が違うので、UAの数値と比較してはいけない |
| **キーイベント(旧: コンバージョン)** | 「これが起きたら成果」と定義した重要イベント | 2024年に「コンバージョン」から**「キーイベント」へ名称変更**された。古い資料や記憶と食い違うので注意 |
| **ディメンション** | 分析の切り口(ページ、デバイス、流入元など) | 「何で分けるか」 |
| **指標(メトリクス)** | 数値(ユーザー数、イベント数など) | 「何を数えるか」 |
| **カスタムディメンション** | 自分で送ったパラメータを、レポートの切り口として使えるようにしたもの | **GA4管理画面での登録が必須**。かつ**登録した時点より後のデータにしか適用されない**(遡って集計できない)。実装したのに見れない、の典型原因 |
| **測定ID** | `G-XXXXXXXXXX` 形式の識別子 | どのGA4プロパティに送るかを決める。開発環境と本番で分けるのが基本 |
| **GTM(Googleタグマネージャー)** | タグを管理画面から出し入れできる別ツール | GA4とは別物。「GTM経由でGA4を入れる」構成も多い。**どちらで実装するかは着手前に必ず確認**すべき |
| **DebugView** | GA4管理画面上で、自分の操作が正しくイベントとして飛んでいるかリアルタイムに確認できる画面 | 実装時の動作確認はここで行う |

### 会話でズレやすい表現

- POが**「コンバージョン」**と言ったら、GA4画面上の**「キーイベント」**のこと(名称変更の過渡期)
- POが**「PV(ページビュー)」**と言ったら、GA4では**`page_view`イベントの発生回数**のこと
- POが**「イベントを追加して」**と言ったら、**コードの実装が必要**なことが多い(拡張計測機能で済むものかどうかを必ず切り分ける)
- POが**「タグを入れるだけでしょ?」**と言ったら、**page_viewは確かにそうだが、業務固有の操作の計測は個別実装が必要**であることを説明する

---

## 6. まとめ: この3点だけ覚えて帰る

1. **GA4はすべてが「イベント」**。ページ表示もクリックも同じ形。UAの知識は捨てる
2. **事前に仕込んだものしか取れない**。「後から遡って見たい」は原則できない。だから**開発の初期段階でPOと計測設計をすり合わせる必要がある**
3. **数値は正確ではない**。ブロッカーやCookie制限で必ず取りこぼす。傾向を見るツールであり、売上の正としては使わない

実際にどうコードを書くかは [GA4の実装ガイド.md](GA4の実装ガイド.md) を参照してください。
